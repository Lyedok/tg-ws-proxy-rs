# v2.2.5

## Lower memory use under load

This release addresses the memory growth reported in issues #97 and #113. The
main leak-shaped cost was not an unbounded Rust collection: every accepted
connection kept an async state machine large enough for the complete fallback
ladder and every bridge variant, even after one route had already won.

- Routing now runs in a short-lived boxed future. Once it selects an upstream,
  synchronous dispatch allocates only that WS, MTProto, or TCP bridge and frees
  the fallback state before the session-long await. A regression test caps the
  outer per-client future at 4 KiB; on x86-64 it fell from 20,784 to 1,808 bytes.
- Every WebSocket now limits incoming frames and messages to 4 MiB instead of
  tungstenite's 16 MiB frame / 64 MiB message defaults. Telegram media parts
  are at most 1 MiB, so this keeps protocol headroom while preventing one odd
  upstream frame from parking tens of megabytes for the connection lifetime.
- The WebSocket write-buffer target is 16 KiB instead of 128 KiB. The bridge
  awaits and flushes every send, so a larger batching target provided no useful
  batching here.
- Traffic counters accumulate in task-local `u64`s and publish once when a
  direction finishes or is cancelled. This removes a mutex acquisition from
  every relay chunk while preserving accurate partial totals on 32-bit MIPS,
  where 64-bit atomics are unavailable.
- MTProto WebSocket packet framing now reads plaintext length headers before
  relay encryption. The splitter no longer decrypts the complete upload a
  second time or retains parallel plaintext and ciphertext buffers; a finished
  encrypted packet moves directly into its WebSocket message.
- TCP sockets now use Tokio's specialized owned read/write halves. This removes
  the shared mutex used by generic `tokio::io::split` from inbound clients,
  upstream MTProto proxies, TCP fallback, and the connectivity checker. In the
  64-client synthetic matrix, direct-WebSocket proxy CPU time fell 2.7% while
  raw-TCP wall time fell 2.1%; other changes were within measurement noise.

The splitter change was measured with 64 simultaneous media sessions, each
transferring eight 1 MiB packets in both directions. Five interleaved runs of
the before/after binaries produced the following medians on Windows:

| Metric | Before | After | Change |
|---|---:|---:|---:|
| Scenario wall time | 2.943 s | 2.704 s | -8.1% |
| Proxy CPU time | 3.281 s | 3.078 s | -6.2% |
| Peak working set | 247.78 MB | 140.74 MB | -43.2% |
| Peak private bytes | 267.39 MB | 163.49 MB | -38.9% |

Every transfer was verified byte-for-byte, including one WebSocket message per
MTProto packet. The same routing matrix also passed in a Linux container.

The included loopback harness drives the release binary through a fake Telegram
TLS/WebSocket endpoint and HTTP CONNECT proxy. It now waits for every upstream
handshake and verifies that every expected transfer drained before reporting
memory. In identical Linux containers with pooling disabled, averaging two
runs in reversed order:

| Workload | v1.7.1 RSS | v2.2.5 RSS | Change |
|---|---:|---:|---:|
| 200 idle WebSocket sessions | 19.87 MB | 19.00 MB | -4.4% |
| 200 sessions, four 256 KiB frames each, peak | 83.98 MB | 79.20 MB | -5.7% |
| Same transfer after every client drained | 40.42 MB | 38.02 MB | -5.9% |

The default `--pool-size 4` was then measured separately, without removing the
media-latency optimization. Both versions held all 16 expected direct-WS
spares (four ordinary and four media connections for each of DC 2 and DC 4):

| Default-pool workload | v1.7.1 RSS | v2.2.5 RSS | Change |
|---|---:|---:|---:|
| 16 ready connections, no clients | 6.48 MB | 6.37 MB | -1.8% |
| 200 idle sessions plus 16 ready connections | 19.75 MB | 18.63 MB | -5.7% |

The post-drain result includes glibc allocator retention and is not a best-case
live-heap snapshot. All three workloads therefore use process RSS rather than
an allocation profiler's narrower live-byte count.

## Compatibility cost

An upstream WebSocket frame or fragmented message above 4 MiB now closes that
upstream connection instead of allocating up to the old limit. This is well
above Telegram's observed 1 MiB media-part ceiling, but a non-Telegram custom
upstream sending larger messages is no longer accepted.
